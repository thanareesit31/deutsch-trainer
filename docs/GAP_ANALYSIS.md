# Gap Analysis: Current System vs Product Baseline

วันที่วิเคราะห์: 2 ตุลาคม 2026  
Source of truth: [PRODUCT_BASELINE.md](./PRODUCT_BASELINE.md)  
เอกสารระบบปัจจุบัน: [current-system-snapshot.md](./current-system-snapshot.md)  
Implementation scope เดิม: [vertical-slice-01.md](./vertical-slice-01.md)

อัปเดตหลัง implementation และ tests วันที่ 2 ตุลาคม 2026. การตรวจยืนยันผ่าน unit tests, PGlite migration/RPC tests, browser flow บน local app, typecheck และ production build; ไม่ได้ตรวจ live Supabase/Vercel. สถานะ schema บนฐานข้อมูลจริงยังต้องยืนยันแยกต่างหาก.

## สรุป

- Core Learn → exposure → gated Practice → attempt/evidence → derived Progress มี implementation ครบใน code และสอดคล้องกับ baseline เป็นส่วนใหญ่
- **พบ P0 1 จุด:** ต้องยืนยันว่า migration ใหม่ถูก apply ครบใน Supabase จริง เพราะ flow ใหม่พึ่งตาราง, view และ RPC เหล่านั้น และมีรายงานก่อนหน้าว่า migration หยุดด้วย `relation "item_exposures" already exists`
- **พบ P1 0 จุดใน behavior ที่แก้รอบนี้:** Pending confidence และ Response Time ผ่านการแก้และทดสอบแล้ว; persistence บน Supabase จริงยังเป็น P0 ที่ต้องยืนยัน
- ไม่พบหลักฐานใน code ว่า Practice บังคับ Learn ซ้ำ หรือว่ามี Not Seen item ผ่านเข้า session: setup/start กรองด้วย exposure และฐานข้อมูลมี FK ป้องกัน

ตัวเลข P0/P1 นับเป็นกลุ่มปัญหาหลักที่ไม่ซ้ำกัน แถว Session persistence, Resume และ Learning History อ้างถึงความไม่แน่นอนเรื่อง migration เดียวกัน จึงไม่ได้นับซ้ำเป็น P0 เพิ่ม

### สถานะและ Priority

- **Aligned:** behavior ตรง requirement ที่ตรวจได้
- **Partially aligned:** implementation มี แต่มีข้อจำกัด/ผลข้างเคียงหรือยืนยัน runtime ไม่ได้
- **Not aligned:** behavior ปัจจุบันขัดกับ requirement
- **Not implemented:** ไม่พบ implementation ของ requirement
- **P0:** ต้องแก้/ยืนยันก่อน เพราะ core flow อาจใช้งานไม่ได้หรือทำงานผิด
- **P1:** สำคัญต่อคุณภาพหรือความถูกต้องของ MVP
- **P2:** ปรับปรุงภายหลังโดยไม่ทำให้ core flow ผิด
- **Later:** อยู่นอก MVP ตาม baseline

## Recommended Implementation Order

1. **ยืนยัน migration 030 บน Supabase จริง (P0).** ตรวจ schema/RPC/view/policy แบบ read-only ก่อน; apply migration แบบ additive ผ่าน workflow ของ project แล้ว smoke test ด้วยบัญชีทดสอบ โดยไม่ลบ/รีเซ็ตข้อมูล
2. **งาน P2 ที่มีอยู่:** ลดความเสี่ยงจาก legacy/aggregate logic ซ้ำและปรับ copy ของ hard-coded content เฉพาะเมื่ออยู่ใน scope; ไม่ใช่ blocker ของ Pending/Response Time ที่แก้แล้ว
3. **Later/Future:** ทำเฉพาะเมื่อกำหนด scope ใหม่

## Safe First Change

**งานแรกที่แนะนำ: ตรวจและใช้ migration `20261003000000_completed_attempts_no_response_time.sql` บน Supabase จริงอย่างปลอดภัย** หลังยืนยัน schema ปัจจุบันแบบ read-only.

- **ทำไมควรเริ่มจากจุดนี้:** local tests ยืนยัน view/RPC ใหม่แล้ว แต่โปรเจกต์เคยพบ migration error `item_exposures already exists`; migration ใหม่ต้องเพิ่ม default และเปลี่ยน KnowledgeState/RPC ให้ Pending ถูกกรอง จึงต้องแน่ใจว่า object ที่มีอยู่ reconcile ได้โดยไม่ทับ/ลบข้อมูล
- **ไฟล์ที่น่าจะได้รับผลกระทบ:** `supabase/migrations/20261003000000_completed_attempts_no_response_time.sql`; หาก migration apply แล้วไม่ต้องแก้ client เพิ่ม
- **สิ่งที่ต้องระวัง:** ห้าม drop/reset table หรือ column; `response_ms` คงไว้; ตรวจ function signature, view, RLS และ policy ก่อนใช้ migration
- **Acceptance criteria หลังแก้:** (1) Supabase ใช้ migration ใหม่ครบ, (2) Pending correct ไม่เข้า Review/Progress/KnowledgeState, (3) easy/thought/guess ทำให้ Attempt Completed, (4) wrong Completed ทันที, (5) reload session กลับมาที่ confidence prompt, (6) response_ms ไม่มีผลต่อ learning logic
